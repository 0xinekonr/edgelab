# 教学模块与会话安排

最后更新：2026-09-11

## 组织原则

本文件定义教学模块边界；`ROADMAP.md` 保留原 Phase 编号。模块可以包含多个 Phase，不按文件、语法点或一次提交拆会话。当前会话完成 M01，之后每个模块使用一个独立的 EdgeLab 项目会话，顺序推进，共用同一仓库。

每个模块可以有多轮教学和多个有意义的提交。先交付结构和接口骨架，再填充实现，最后集中验证。核心源码和构建文件由用户手写；Codex 静态检查、讲解并维护中文文档。重点 C++ 机制必须在参考代码注释中解释职责、原理和 Java 差异。

## 顺序与范围边界

- 保持现有路线图的主要依赖顺序。M03 使用现有接收 API 验证网关，并允许增加必要的批量接收契约；持久化与完整去重机制在 M04 落地。
- C++ 手写重点集中在 M02、M03 的协议、缓冲、并发和边缘处理。最小 HTTP 客户端用于理解网络和资源管理；后续网关使用成熟 HTTP 库前，比较现有实现并保留明确的上报边界，不把课程扩展成完整 HTTP/TLS 库开发。
- M03 先使用受限内存队列；在需要跨进程重启补发时，再加入本地持久缓冲及恢复机制。明确哪些数据可能丢失，不声称天然实现端到端 exactly-once。
- M06 只选一种消息队列；M08 按职责选择必要的 Spring Cloud 组件；进入模块时核对版本兼容性。避免为了覆盖组件而同时引入同类框架。
- 本地模拟贯穿所有模块：依赖某项基础设施时就补启动说明和可复现输入，M10 负责汇总验收。规模受本机资源约束，大数据学习侧重分区、窗口、状态与恢复，而非堆积数据量。
- Java/C++ 首先通过进程间协议协作。JNI 不列为强制主线；只有出现可衡量的进程内调用需求时，再作为扩展模块，说明 ABI、内存所有权和故障隔离成本。
- M10 的 Linux 构建保留 Windows 日常开发习惯；平台专属网络实现须替换或隔离后才能宣称可移植。

5. 在新的项目会话开始 M02。本会话不继续展开协议教学。

## 会话交接流程

模块开始时，先读 `AGENTS.md` 和状态文档，再读取本文件、相关源码与 diff；确认上一模块的验证结果及遗留限制。为当前模块更新 `CURRENT_PLAN.md`，再给出本轮完整功能包的教学。

模块结束时，Codex 必须：

1. 做静态检查，记录实际验证证据；区分用户报告、Codex 执行与尚未验证的项目。
2. 更新 `PROJECT_STATE.md`、`HANDOFF.md`、`CURRENT_PLAN.md` 和相关路线图状态。HANDOFF 写清完成能力、已知限制、关键文件、验证命令和结果、分支/提交/PR 状态、下一模块入口。
3. 提醒用户按完整功能块提交并 push；PR 是否合并依据实际状态记录，不自动提交、push 或合并。
4. 提供下一会话标题与启动提示。届时优先复用已存在的对应模块会话；在上一模块验收和 Git 状态明确后，按用户已授权的独立项目会话安排创建下一个。只创建即将开始的模块，不提前批量创建；工具不可用时提供手动入口。

新会话沿用同一项目，开始前核对实际 checkout、分支及工作区。独立会话不代表新仓库，也不要求用户重复搭建工程。若新会话在 worktree 中启动，先核对提交基线并配置所需构建环境，不能假设旧工作区的未提交代码和构建产物已经存在。

下一会话建议标题：`EdgeLab M02：设备协议与增量编解码`。

